# 架构说明

## 为什么是这个形状

这个项目一开始是个纯静态页（选手墙画死在 HTML 里）。后来需求一个个加上来——
投票、排行榜、小游戏额度、直播条、标签——每一步都在加"需要跨访客共享的状态"。

摆在面前有三条路：

| 方案 | 结果 | 结论 |
| --- | --- | --- |
| 全塞进前端 + localStorage | 换台设备数据就没了；排行榜无法共享 | 不可行 |
| 引一个 BaaS 直接让前端连数据库 | 前端必须拿到数据库凭据 → **等于把它公开** | 不可行 |
| 前端 ← 单个云函数 ← 数据库 | 前端零密钥，规则全在服务端 | **选这条** |

所以就有了现在这个"一个 HTTP 云函数当唯一闸门"的结构。
它带来两个直接后果，也是这个项目最重要的两个不变量：

1. **前端可以随便改，改不出用不了的版本。** 额度、局次、分数合法性全在服务端裁定。
2. **前端泄露不了任何东西。** 它真的没有任何东西可泄露——没有密钥、没有连接串。

## 三层结构

### 第一层：静态前端

`web/index.html` 是**单文件**：HTML、CSS、JS 全内联，没有构建步骤，没有 npm。

这不是偷懒，是刻意的：

- 部署 = 传文件。没有 CI、没有 `node_modules`、没有版本漂移。
- 断网也能开（页面有完整的离线兜底数据）。
- 十年后还能打开。

代价是文件很大（约 200 KB），以及改代码需要在同一个文件里找位置。
对一个小型赛事站来说这个交换是划算的。

页面内部的模块划分（按代码里的注释分节）：

| 节 | 职责 |
| --- | --- |
| 0. 设计令牌 | 从游戏实机取色的 CSS 变量 |
| 1–3. 布局 / 卡片 / 导航 | 选手墙、筛选、搜索 |
| 4. 云端同步层 | 应援计数、额度、JSONP/XHR 双通道 |
| 5. 打捞小游戏 | Canvas 主循环、难度曲线、结算 |
| 6. 排行榜 | 提交昵称、渲染榜单 |
| 7. 规程切片 | 长图分段懒加载、双阅读模式 |
| 8. 占卜 | 藏品单抽与吉凶特效 |
| 9. 直播条 | 吸顶总台入口、三态渲染 |
| 10. 选手标签 | 云端标签渲染 |

### 第二层：云函数 `server/index.js`

**约 630 行，零依赖**——只用 Node 内置的 `http` / `https`，不装任何 npm 包。

它做四件事：

1. **路由**：按 query 参数决定走哪条业务分支（下面有完整列表）。
2. **校验与清洗**：设备号正则、昵称去控制字符、按码点截断、数值夹紧。
3. **限流**：管理密钥试错计数（5 分钟 30 次）。
4. **代理**：代前端向 B 站拉直播状态，绕开 CORS 并做 45 秒缓存。

它**不做**业务规则。额度够不够、这一局合法不合法、分数能不能信——全部在数据库函数里。
云函数只是一根管子。

### 第三层：PostgreSQL 函数

所有业务规则都在这里，用 `SECURITY DEFINER` 函数实现。

这样做的原因是**它绕不过去**：函数体在数据库里，改前端、改云函数、甚至拿到云函数源码
都改变不了"每天只有 50 次"这件事。

## 数据模型

### 表

| 表 | 主键 | 存什么 | `anon` 权限 |
| --- | --- | --- | --- |
| `cheer_bonus` | `(device_id, day)` | 当日额外额度、最高分、最深层数、局数 | 只读 |
| `cheer_game_token` | `token` | 单局令牌、所属设备、是否已用 | **无** |
| `game_score` | `device_id` | 昵称、分数、层数、遗物数、连击数 | **无** |
| `cheer_counts` | `player_id` | 每位选手的累计票数（**只存总数**） | 只读 |
| `site_live` | `id = 1`（单行） | 当前总台的房间号 / 标题 / 备注 / 开关 | **无** |
| `site_secret` | `name` | 管理口令 | **无** |
| `player_tag` | `(player_id, tag)` | 选手标签 + 排序 | **无** |

**注意 `game_score` 对 `anon` 完全不授权。** 这张表里有 `device_id`，
如果开放直读，任何人都能拿到"设备 ↔ 昵称 ↔ 成绩"的对应关系。
排行榜走的是另一个只输出展示字段的函数。

### 函数

| 函数 | 类型 | 作用 |
| --- | --- | --- |
| `cheer(player_id, device_id, limit)` | 写 | 投一票。超额时返回 `{ok:false, reason:'limit'}`，不抛异常 |
| `cheer_status(device_id, limit)` | 读 | 该设备今天的已用 / 剩余额度 |
| `cheer_counts()` | 读 | 全站票数快照（只读表，云函数直接查） |
| `game_start(device_id)` | 写 | 开局，发一枚一次性令牌 |
| `game_reward(...)` | 写 | 结算：校验令牌 → 按层数发额度 → 落排行榜 |
| `game_bonus(device_id)` | 读 | 该设备今天赢到的额外额度（0–50） |
| `game_layer_tier(layer)` | 纯函数 | 层数 → 票数：`min(50, layer × 5)` |
| `game_leaderboard(limit)` | 读 | 榜单。**只出昵称 / 分数 / 层数 / 遗物 / 连击，不含 device_id** |
| `game_nick_clean(nick)` | 纯函数 | 昵称清洗（去控制字符、压空白、截断） |
| `live_get()` | 读 | 当前总台配置 |
| `live_set(key, ...)` | 写 | 改总台配置（凭口令） |
| `tag_get()` | 读 | 全部标签，一次返回整张表 |
| `tag_set(key, player_id, tags)` | 写 | 覆盖某选手的全部标签（**整组替换**，凭口令） |
| `admin_check(key)` | 读 | 管理台门禁。**只回答对错，不写任何数据，不回长度/前缀** |

`sql/` 下的六个文件按序号执行即可建出上面全部内容，语句都是幂等的。

### 为什么是"整组替换"

`tag_set` 的语义是把某位选手的标签**整个换掉**（先 DELETE 再按序 INSERT），
而不是增量增删。

这样设计是因为增量接口需要在客户端维护"我上一轮发了什么"的状态，
一旦用户在两个标签页同时开着管理台，就会出现"删一半"的中间态。
整组替换让每次写入都是自洽的最终状态，重发也不会有副作用。

## 云函数的完整路由

| 请求 | 说明 | 需要设备号 |
| --- | --- | --- |
| `GET /?deviceId=X` | 票数快照 + 该设备额度 | ✅ |
| `GET /?deviceId=X&vote=N` | 投票（`<img>` 信标兜底通道） | ✅ |
| `POST / {deviceId, playerId}` | 投票（主通道） | ✅ |
| `GET /?deviceId=X&gameStart=1` | 开局取令牌 | ✅ |
| `POST / {deviceId, score, token, ...}` | 结算成绩 | ✅ |
| `GET /?leaderboard=1&limit=20` | 排行榜（公开只读） | ❌ |
| `GET /?live=1` | 当前总台 + B 站实时状态 | ❌ |
| `GET /?tags=1` | 全部选手标签 | ❌ |
| `GET /?auth=1&key=K` | **门禁：只读验钥** | ❌ |
| `POST / {liveSet:true, key, ...}` | 改总台（凭口令） | ❌ |
| `POST / {tagSet:true, key, ...}` | 改标签（凭口令） | ❌ |

任意请求加 `&callback=fn` 会返回 JSONP。

### 为什么要有 JSONP 和 `<img>` 信标

目标用户大量在 QQ / 微信内置浏览器里打开页面，那些 X5 内核的浏览器：

- `fetch` 和 `AbortController` 支持不完整；
- 跨域 XHR 有时直接被拦；
- 看到 `Content-Disposition: attachment` 可能把响应交给下载器。

所以每个写操作都有三条降级通道：**XHR POST → XHR GET → JSONP → `<img>` 信标**。
信标通道靠 URL 参数传数据，因此云函数对投票这条路径同时接受 `body.playerId` 和 `?vote=`。

副作用是响应里必须显式覆盖 `Content-Disposition: inline`，以及 JSONP 回调名必须走白名单
（否则就是经典的 JSONP XSS）。

## 前端的几个不变量

改这份代码时请守住：

1. **选手名称永不截断。** 用 `flex-wrap` 换行，不用 `text-overflow: ellipsis`。
   代码库里 `ellipsis` 的出现次数应该是 **0**。
2. **`[hidden]` 必须显式声明。** 页面上好几个容器是 `display: flex`，
   会盖掉 `hidden` 属性自带的 `display: none`。CSS 里有一条
   `[hidden] { display: none !important; }` 兜住。少了它，管理台在门禁通过前
   会把整个控制台渲染出来。
3. **管理台的 id 不能重复。** 两个页签合并到一页后，`id="msg"` 这类通用名字会串台——
   `getElementById` 只认文档里第一个。前缀化（`msgLive` / `msgTags`）。
4. **名单是"第二份真相"。** `index.html` 的 `PLAYERS_DATA`、`admin.html` 的 `ROSTER`、
   `assets/data/players.json` 各存一份选手信息。改赛事要同时改三处，
   id 顺序必须逐位一致（数据是按 id 关联的）。建议保留一条静态断言兜住这个不变量。

## 已知的架构级取舍

| 取舍 | 换来 | 代价 |
| --- | --- | --- |
| 单文件前端 | 零构建、十年可开 | 文件大；无 CSP 可用 |
| 云函数当唯一闸门 | 前端零密钥 | 多一跳延迟；单点 |
| 用 `device_id` 当身份 | 完全匿名 | **票数可刷** |
| 业务规则在 SQL 里 | 前端绕不过 | 逻辑分散在两个文件里读 |
| 整组替换式写入 | 无中间态 | 每次请求都发全量标签 |
| 只绑 CloudBase PostgREST | 少写一层数据访问代码 | 换云厂商要改 `restCall()` |

最后一条值得展开：`server/index.js` 里的 `restCall()` 直接打的是
`https://<env>.api.tcloudbasegateway.com/v1/rdb/rest`。
如果你想搬到别的云，改掉这个函数（换成 `pg` 客户端直连即可）就能跑，业务逻辑不用动。
